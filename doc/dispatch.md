# Command model and dispatch

Implemented in `cli_dispatch()` in [`src/cli.c`](../src/cli.c).

## The command tree

A command table is an array of `cli_cmd_t`. Any entry may carry its own
`subcmds` table, so the tree nests to arbitrary depth. The lookup walk is
iterative, so depth costs no stack.

```
commands[]
├── led            (subcmds, no handler)   → "led" alone is an error
│   ├── on         (handler)
│   ├── off        (handler)
│   └── blink      (handler, args)
├── i2c            (subcmds, no handler)
│   └── scan       (handler, args)
└── echo           (handler, variadic arg)
```

Lookup is case-**sensitive** and uses `strcmp`, matching the whole word.
Commands are searched in table order; the built-in table (`help`, `history`) is
searched *after* the application table, so an application command named `help`
shadows the built-in.

## Resolution algorithm

1. `cli_lookup_top()` matches `tokens[0]` against the application table, then
   the built-ins. No match → `error: unknown command '<x>'` plus the hint to
   type `help`, return `CLI_ERR_UNKNOWN_CMD`.
2. While the current node has subcommands, try to match the next token against
   them.
   * **Match** → descend, append the name to the diagnostic path, consume the
     token, repeat.
   * **No match, and the node has a handler** → stop descending; the remaining
     tokens become this node's arguments.
   * **No match, and the node has no handler** → error, list the available
     subcommands, return `CLI_ERR_UNKNOWN_SUB`.
3. If the resolved node has no handler, report `'<path>' cannot be executed
   directly` and list its subcommands.
4. `cli_build_args()` validates arity and converts each token.
5. The handler runs. A non-zero return is reported as
   `error: '<path>' returned <n>` and propagated.

### The handler/subcommand overlap rule

This is the one piece of behaviour worth internalising:

| Node has `subcmds` | Node has `handler` | Effect of an unmatched next token |
|---|---|---|
| yes | no | error — a subcommand is **required** |
| yes | yes | the token becomes the node's **first argument** |
| no | yes | the token becomes the node's first argument |
| no | no | `'<path>' cannot be executed directly` |

So a node with both a handler and subcommands is ambiguous by design: a word
that happens to name a subcommand always wins over being an argument. Avoid
giving such a node a first argument whose plausible values collide with
subcommand names.

## Diagnostic paths

The path string (`"led blink"`) is accumulated in a fixed `CLI_PATH_LEN` (64)
byte buffer as the walk descends, and is used for every error message and for
`cli_print_usage()`. Appending stops silently once the buffer is full, which
only affects the text of a diagnostic, never the dispatch itself.

A handler that wants to print its own usage should pass the same path it was
invoked under; there is no way to recover it from the `cli_args_t`, so
hard-code it or keep a pointer in `cfg.user`.

## Arity validation

`cli_build_args()` derives the bounds from the spec:

* **minimum** = number of specs with `optional == false`
* **maximum** = `CLI_MAX_ARGS` when the last spec is `variadic`, otherwise the
  number of specs

Failure modes, in the order they are checked:

| Condition | Message | Status |
|---|---|---|
| more tokens than `CLI_MAX_ARGS` | `too many arguments` | `CLI_ERR_OVERFLOW` |
| command declares no args but got some | `'<path>' takes no arguments` + usage | `CLI_ERR_ARG_COUNT` |
| fewer than the minimum | `missing argument` + usage | `CLI_ERR_ARG_COUNT` |
| more than the maximum | `too many arguments` + usage | `CLI_ERR_ARG_COUNT` |
| a token fails conversion | `argument N <name>: '<tok>' is not a valid <type>` | `CLI_ERR_ARG_TYPE` |

For a `CLI_ARG_ENUM` mismatch the message also lists the accepted values, so no
extra help text is needed.

Tokens beyond the number of specs reuse the **last** spec — that is what makes
`variadic` work, and it is also why `variadic` on a non-final spec is
meaningless.

## Built-in commands

Compiled in unless `CLI_ENABLE_BUILTINS` is 0.

### `help [<command>...]`

With no argument, prints every command name and its `help` text in a column
aligned to the widest name, application table first. With arguments, it walks
the same path through the tree and prints the node's description, its generated
usage line, and its subcommand table.

The `help` argument spec is a single `optional`, `variadic` `CLI_ARG_STR`,
which is how `help led blink` works.

### `history`

Lists the history ring oldest-first with 1-based indices. Compiled out when
`CLI_HISTORY_DEPTH` is 0, independently of `CLI_ENABLE_BUILTINS`.

## Usage line format

Generated by `write_arg_spec()` in [`src/cli_builtin.c`](../src/cli_builtin.c):

| Spec | Rendered as |
|---|---|
| required | `<name:type>` |
| optional | `[name:type]` |
| string | `<name>` — no type annotation, since it always matches |
| enum | `<name:a\|b\|c>` |
| variadic | `...` before the closing bracket, e.g. `[name:integer...]` |

A node with subcommands adds `<subcommand>`, or `[<subcommand>]` when it also
has a handler — which reads exactly as the overlap rule behaves.

Per-argument `help` strings, when present, are printed underneath the usage
line.
